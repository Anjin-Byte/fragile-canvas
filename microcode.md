# Primitives for Implementing the Sharp SM83 (Game Boy) CPU Instruction Set

To emulate the Game Boy’s Sharp SM83 CPU, we identify a minimal set of **software-level logic primitives** that can reproduce all instruction behaviors. These primitives are grouped by function: memory/register access, arithmetic/logic, bit operations, stack, control flow, and system/interrupt controls. For each instruction (or family of instructions), we note how it breaks into micro-operations, which primitives it uses, any special timing or global-state effects (flags, pipelining, etc.), and any exceptional quirks.

## Memory and Register Access Primitives

- **Register-to-Register Load (8-bit):** Simply copies an 8-bit value from one CPU register to another (e.g. `LD B, C`). This is a single micro-op: read source register and write to destination. No flags are affected. It cannot be broken down further except as a trivial data transfer. All such `LD r1, r2` instructions execute in one cycle on real hardware and have no special timing considerations beyond the standard fetch and write-back.

- **Immediate to Register Load (8-bit/16-bit):** Fetches an immediate constant from the next byte(s) of program memory into a register. For 8-bit immediates (`LD r, n`), the emulator performs a memory read at PC, increments PC, and writes the byte to the target register ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,addr%3DBC%2C%20data%3DA)). For 16-bit immediates (`LD rr, nn` for BC, DE, HL, SP), two sequential memory reads are done (least significant byte then most significant), combined into a 16-bit value. These break down into micro-ops: read low byte, increment PC, read high byte, increment PC, write both into the 16-bit register. No flags are affected. Timing is typically 2 machine cycles (16-bit loads take an extra cycle for the second byte). The only *global state* effect is PC advancement by 2 or 3 bytes as appropriate.

- **Register to Memory Store (8-bit):** Writes an 8-bit register into a memory location. The addressing modes include:
  - **Direct 16-bit address:** e.g. `LD (nn), A` uses a 16-bit immediate address. It requires reading the 16-bit address from the instruction stream and then a memory write. In micro-ops: fetch low address byte, fetch high address byte, then `write_memory(addr, A)` ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M1%20M2)). No flags are modified. This instruction takes 3 machine cycles (two for operand, one for write).
  - **Register-indirect:** e.g. `LD (HL), A` or `LD (BC), A`. Here the address comes from a register pair. The primitive steps: compute the 16-bit address from registers (HL or BC/DE), then write the A register to that address ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=LD%20,bit%20A%20register)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,addr%3DBC%2C%20data%3DA)). Treated as one memory write operation in software. No flags changed. Takes 2 cycles on hardware (one for fetch, one for memory write).
  - **High-page (FF00) address:** e.g. `LD ($FF00+C), A` or `LD ($FF00+n), A`. These use an 8-bit offset added to 0xFF00 (for gamepad/IO registers). The emulator can implement this as an address calculation primitive: `addr = 0xFF00 + offset`. Then perform a memory write. No flags or special timing beyond the normal 2 cycles (the offset is often the byte after the opcode for the `n` case). 

- **Memory to Register Load (8-bit):** Reads an 8-bit value from memory into a register. Addressing modes mirror the above:
  - **Direct 16-bit address:** `LD A, (nn)` reads from an absolute address given in the next two bytes. Micro-ops: fetch 16-bit address, then `A = read_memory(addr)` ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,addr%3DBC)). No flags affected. (2 cycles to fetch address + 1 for read = 3 cycles total).
  - **Register-indirect:** `LD A, (HL)`, `LD A, (BC)` etc. Compute address from register pair and perform memory read ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M1%20M2)). One memory access needed (2 cycles). No flag changes.
  - **High-page address:** `LD A, ($FF00+C)` or `LD A, ($FF00+n)` does the FF00 offset calculation and memory read similarly. No flags.  

- **Indirect Loads with HL Increment/Decrement:** The instructions `LDI A, (HL)` / `LDI (HL), A` and `LDD A, (HL)` / `LDD (HL), A` perform a memory read or write at address HL *and then adjust HL*. They combine the above primitives with a 16-bit increment or decrement on HL. For example, `LDI A,(HL)` reads from `addr=HL` into A, then does `HL = HL + 1`. The minimal primitives are: a memory read and a 16-bit add (HL+1). Likewise, `LDD` uses HL–1. In hardware these still take 2 cycles (the ALU handles the HL update in the second cycle). No flags are affected by the HL pointer change (these HL auto-inc/dec operations do *not* update the flag register). The only caveat is a known **hardware quirk**: on older models, if `HL` falls in the range $FE00-$FEFF (OAM memory) when using `LDI/LDD` or 16-bit inc/dec, an unintended write to OAM can occur ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=When%20the%20following%20instructions%20are,not%20affected%20by%20these%20instructions)) (a design bug causing sprite corruption). A software emulator might ignore this unless striving for cycle-accurate hardware glitches.

- **Load SP from HL:** The instruction `LD SP, HL` copies the 16-bit HL into SP ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,0xF9%3A%20SP%20%3D%20HL)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Previous)). This is a single 16-bit transfer primitive (read HL, write SP) and does not affect flags ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b11111001%2F0xF9%20Duration%202%20machine,Simple%20timing%20and%20pseudocode)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200xF9%3A,PC%20%3D%20PC%20%2B%201)). It effectively executes in 2 cycles (one for fetch, one for the 16-bit assign). No special micro-ops beyond a direct register assignment, and no flags or unusual timing.

- **Load memory from SP (Store Stack Pointer):** `LD (nn), SP` stores the 16-bit SP value to a given address. This is implemented by splitting SP into two bytes and writing them to memory at `nn` and `nn+1`. In micro-ops: fetch 16-bit address, then write low byte of SP, increment address, write high byte of SP ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20IR%20%3D%3D%200x08%3A%20Z,M6%2FM1)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=,PC%20%3D%20PC%20%2B%201)). This uses the basic memory write primitive twice. It takes 5 machine cycles (1 fetch + 2 writes + overhead). No flags affected. The ordering is little-endian (low 8 bits stored first) as shown by the pseudocode ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=,M6%2FM1)).

**Timing/State:** Most load/store operations simply consume CPU cycles proportional to the number of bytes transferred. There is usually a one-to-one correspondence between these software primitives and hardware machine cycles (e.g. one cycle per immediate byte or memory access). There is no overlap of fetch/execute beyond the normal prefetch of the next opcode. The Program Counter is incremented appropriately after each immediate byte fetch or opcode. No condition flags are changed by pure data moves (except incidental cases like loading into AF where the F register bits are flags themselves, but that’s just data assignment). 

**Exceptions:** These operations are straightforward and generalizable. One edge case is the **STOP instruction’s second byte** (0x00) which acts like an immediate but is generally ignored – see STOP under system instructions. Also, high-page loads (`LDH`) are a special-case address calculation but trivial to implement. Memory/register access primitives do not usually interact with global state, except that misuse of certain addresses can trigger hardware quirks (like the OAM bug above) which are outside normal CPU logic.

## Arithmetic and Logical Primitives (8-bit and 16-bit)

The SM83’s arithmetic/logic instructions revolve around an 8-bit ALU that sets condition flags (ZF,Z; NF,N; HF,H; CF,C). Each can be broken into micro-ops: fetching operands (from register, memory, or immediate), performing the ALU operation, storing the result, and updating flags. Notably, the SM83’s hardware ALU operates on 4-bit halves internally (setting the half-carry flag if a carry from bit3->bit4 occurs), which can require two internal steps for 8-bit operations ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x80%3A%20,7%5D%20else%200)). For 16-bit operations, the 8-bit ALU is invoked twice (low byte then high byte), which affects timing and flag computation. In emulation, we can treat these as single operations while reproducing the flag effects.

- **8-Bit Addition (A + n):** Adds an 8-bit value to the accumulator A. This covers `ADD A,r`, `ADD A,(HL)`, `ADD A,#` (immediate). Required primitives: fetch the operand (from register, memory, or immediate) and an 8-bit add operation that produces a result and carry bits. The ALU primitive returns both the 8-bit sum and carry-out of bit 3 and bit 7, to set flags. The result is written back to A. Flags: Z is set if result is 0, N=0 (addition), H is set if there was a carry from bit3, C is set if carry from bit7 (overflow beyond 0xFF). For example, `ADD A, B` does `A = A + B` then sets Z if A=0, H if (A_low_nibble + B_low_nibble > 0xF), C if (A + B > 0xFF). This instruction executes in one machine cycle. In micro-ops it’s a single ALU step, but internally the hardware might do it nibble by nibble (this is invisible except via H flag). No special global-state issues; it’s purely combinatorial logic plus flag register update.

- **8-Bit Addition with Carry (ADC A, n):** Adds operand plus the carry flag C to A. It uses the same primitive as ADD but includes the current C flag as an input (treating it as 1 if C=1, else 0) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200xCE%3A,3%5D%20else%200)). This can be broken into: read operand, compute `A + operand + (C?1:0)`. Flags are set similarly (Z, H, C as above; N=0). The half-carry takes into account the carry-in as well. For example, if A=0x8F, C=1, and adding 0x01, the half-carry flag would consider 0xF + 0x1 + 0x1 carry-in wrapping from low nibble. The emulator’s primitive should handle this. ADC’s timing is the same as ADD. The only nuance is dependency on the prior C flag state (global flag input). No other special effect.

- **8-Bit Subtraction (A – n):** Subtracts an 8-bit value from A. This covers `SUB A,r`, `SUB A,(HL)`, `SUB A,#`. It uses an 8-bit subtract ALU primitive. In implementation, this can be done by two’s complement addition or direct subtraction as long as we compute the borrow/half-borrow. Flags: Z set if result 0, N=1 (subtraction), H set if a borrow from bit4 occurred, C set if a borrow from bit8 occurred ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x90%3A%20,7%5D%20else%200)). (Another way to get H is check if `(A & 0xF) < (operand & 0xF)` for borrow out of bit3.) For example, `SUB B` does `A = A - B`, sets N=1 and flags H,C based on the borrows ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x90%3A%20,7%5D%20else%200)). Like addition, this is one ALU operation (though hardware may do nibble steps, setting H accordingly). No special timing beyond 1 cycle. 

- **8-Bit Subtraction with Carry (SBC A, n):** Subtracts operand and the carry flag (treated as “borrow-in”) from A. Requires the same primitive as SUB but including the current carry flag in the subtraction: effectively `A = A - operand - (C?1:0)`. Flags are set as for subtraction (N=1; Z, H, C according to result and borrows) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200xB8%3A%20,7%5D%20else%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20IR%20%3D%3D%200xB8%3A%20,PC%20%3D%20PC%20%2B%201)). This operation’s half-carry and carry logic must account for the borrow-in. (In practice, an emulator can compute `result = A - operand - carry_in`, then set H if `(A & 0xF) < ((operand & 0xF) + carry_in)`, and C if a full 8-bit borrow occurred ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20A%20,7%5D%20else%200)).) No extra timing beyond 1 cycle, but it depends on global C flag state. No other global effects.

- **Compare (CP n):** This instruction is essentially a subtraction that *does not store the result*. It subtracts the operand from A, sets flags as if `A - n` was executed, but A is left unmodified ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=CP%20r%3A%20Compare%20,not%20update%20the%20A%20register)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200xB8%3A%20,7%5D%20else%200)). We can implement this by performing the subtraction in a local temp variable or ALU output, then setting Z,N,H,C based on it, without altering A. Flags: Z=1 if A == n, N=1, H and C as in a subtraction (indicating if borrow from bit4/bit8 occurred) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200xB8%3A%20,7%5D%20else%200)). Because A is unchanged, it has no further effect on state. (On hardware this is done by the ALU but suppressing the write-back to A ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=CP%20r%3A%20Compare%20,not%20update%20the%20A%20register)).) Timing is identical to a SUB. No special cases except that it’s a “flags only” operation.

- **8-Bit Logical AND:** Performs bitwise AND between A and the operand, stores result in A. The ALU primitive is a simple bitwise AND. Flags: Z=1 if result is 0, N=0, **H=1**, C=0 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,C%20%3D%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%20%3D%20A%20%26%20B,H%20%3D%201)). (Notably, the half-carry flag is set to 1 for an AND in Game Boy, inheriting Z80’s quirk – this doesn’t represent a real binary carry, it’s just defined that way). This is a single micro-op (A = A & n). No carries are actually propagated, but we set H=1 unconditionally ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%20%3D%20A%20%26%20B,H%20%3D%201)). Takes 1 cycle (or 2 if reading from memory). No global state issues.

- **8-Bit Logical OR/XOR:** Bitwise OR or XOR between A and operand, result in A. Both are single ALU operations. Flags: Z=1 if result is 0; N=0; H=0; C=0 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,C%20%3D%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20IR%20%3D%3D%200xB0%3A%20,PC%20%3D%20PC%20%2B%201)). (OR and XOR clear the half-carry and carry flags.) These also take 1 cycle (plus operand fetch if needed). No special micro-ops beyond the logic operation. No exceptional behavior.

- **Increment (INC) 8-bit:** Adds 1 to a register or memory byte. This is effectively a specialized add: operand + 1. We treat it as an ALU operation with a constant 1. Importantly, the carry flag is *not* affected by INC/DEC (so we don’t touch C). Flags: Z is set if the result is 0; N=0 (since it’s like an addition); H is set if there was a carry out of bit3 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x04%3A%20,3%5D%20else%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20B%20%2B,PC%20%3D%20PC%20%2B%201)); C is unchanged. For example, `INC B` does `B = B+1`, sets Z if B becomes 0x00, sets H if `(B & 0xF) + 1 > 0xF` ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x04%3A%20,3%5D%20else%200)). Micro-ops: read B, add 1, write back B, update flags (preserving old C). If the target is `(HL)` (memory), it requires a read-modify-write: fetch value at HL, add 1, write it back ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,3%5D%20else%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x34%3A%20data,3%5D%20else%200)). Hardware performs this in 2 cycles (one for read, one for write), and the emulator should do the same logically. No global effects besides flags.

- **Decrement (DEC) 8-bit:** Subtracts 1 from a register or memory byte. Similar to INC, using an ALU subtract of 1. Flags: Z=1 if result is 0; N=1 (since it’s subtraction) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,3%5D%20else%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%2FM1%20if%20IR%20%3D%3D%200x05%3A,3%5D%20else%200)); H is set if a borrow from bit4 occurred (i.e. if the lower nibble was 0 before decrement) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%2FM1%20if%20IR%20%3D%3D%200x05%3A,3%5D%20else%200)); C is unchanged. Example: `DEC B` does `B = B-1`, sets N=1, sets H if `(B & 0xF) == 0x0` before decrement (because 0x0 -> 0xF causes a half-borrow) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%2FM1%20if%20IR%20%3D%3D%200x05%3A,3%5D%20else%200)). No effect on carry flag. Memory decrement `DEC (HL)` is a read-modify-write similar to INC. No special behavior beyond flags.

- **16-Bit Addition (ADD HL, rr / ADD SP, e):** Adds a 16-bit value to 16-bit HL, or adds a signed 8-bit offset to SP. The SM83 uses the 8-bit ALU twice for 16-bit adds ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200x09%3A,C)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20H%20%2B,PC%20%3D%20PC%20%2B%201)). We can implement this with two 8-bit adds: lower byte and then upper byte with carry. The required primitives are the 8-bit add (with carry) and handling of flags:
  - For `ADD HL, rr`: HL = HL + rr (where rr = BC, DE, HL, or SP). Flags: N=0 (it’s an addition), Z is unaffected (Z flag remains as it was – Game Boy does **not** change Z on 16-bit ADD) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x09%3A%20,15%5D%20else%200)), H is set if carry from bit11 to bit12 occurred, C is set if carry from bit15 to 16 occurred ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x09%3A%20,15%5D%20else%200)). In practice, after computing the 16-bit sum, H can be determined by checking if `(HL & 0x0FFF) + (rr & 0x0FFF) > 0x0FFF` (carry out of lower 12 bits) and C by if result > 0xFFFF. The hardware does: add low bytes (setting a provisional H and C), then add high bytes + carry, setting final H and C ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200x09%3A,C)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20H%20%2B,PC%20%3D%20PC%20%2B%201)). An emulator can compute 16-bit result directly but must replicate the correct H flag (which effectively comes from bit11). Timing: these take 2 cycles on hardware. In micro-ops: fetch opcode, do two ALU ops. There’s a slight *timing quirk* due to the 4-bit ALU: internally it might take 2 ALU cycles for each byte, but that just reflects the 2 machine cycles total.
  - **ADD SP, e (8-bit signed offset):** This adds a signed 8-bit immediate to SP (used for stack pointer adjustment). It is similar to 16-bit addition but a special case: **Z and N flags are cleared to 0**, while H and C are set according to the low-byte addition of SP and the offset ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,7%5D%20else%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20SP%20%2B,7%5D%20else%200)). The half-carry here is defined as carry from bit3 of the low byte, and C as carry from bit7 of the low byte, after adding the signed value (this is effectively treating the operation as two’s complement addition). The result is stored in SP. Example: if SP=0xFFF0 and offset = +0x10, then SP becomes 0x0000, H=1 (carry from 0xF + 0x0 = 0x10 carry from bit3) and C=1 (carry from 0xFF + 0x10 = past 0xFF) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20SP%20%2B,7%5D%20else%200)). In micro-ops, the hardware actually adds the low 8 bits and then the high 8 bits with carry (and sign-extension) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,7%5D%20else%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=HL%20%3D%20result%20flags,7%5D%20else%200)), but only H and C from the **low-byte calculation** are documented as the flag results. Timing: `ADD SP, e` is 4 cycles (since it reads an immediate and does two 8-bit adds). It has a global timing implication in that it’s a 2-byte instruction that takes an extra cycle compared to other 16-bit adds, due to sign extension and separate flag handling.

- **16-Bit Increment/Decrement:** Instructions `INC rr` and `DEC rr` (where rr = BC, DE, HL, SP) increment or decrement a 16-bit register by 1. These do **not** affect any flags ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=%3B%20rr%20is%20bc%2C%20de%2C,or%20hl)). They can be implemented with two 8-bit adds (low part +1, then high part + carry for INC; analogous subtract for DEC) or simply as a 16-bit add/sub without flags. In hardware they execute in 2 cycles. The only potential irregularity is the OAM DMA bug mentioned earlier: if `HL` is in $FE00-$FEFF and you do `INC HL` or `DEC HL`, old Game Boy models erroneously write to OAM (sprite memory) ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=When%20the%20following%20instructions%20are,not%20affected%20by%20these%20instructions)). In a high-level emulator, one would normally ignore this unless cycle-accuracy is needed. Aside from that, these are straightforward (no flags, just 16-bit arithmetic). 

- **Decimal Adjust Accumulator (DAA):** This is a special **BCD correction** operation applied to A after a binary add or sub of packed BCD digits. It cannot be expressed as a simple logic or arithmetic operation – it involves conditional additions. The primitive for DAA must check the half-carry (H) and carry (C) flags and the *N flag (add vs sub)* to decide the correction. In essence: if the previous operation was an addition (N=0) and (if lower 4 bits > 9 or H=1) then add 0x06 to A; if (if upper 4 bits > 9 or C=1) then add 0x60 to A. For subtraction (N=1), the adjustments are slightly different: if H=1, subtract 0x06; if C=1, subtract 0x60 ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=The%20Game%20Boy%20STOP%20instruction,the%20second%20byte%20is%20ignored)). An emulator’s implementation will do these checks and adjust A accordingly. Flags after DAA: Z is set if A becomes 0; H is reset to 0 (the Game Boy’s DAA clears H flag after execution); N remains as it was (indicating the operation type); C is set if an 0x60 carry-out correction was applied (i.e. if A was > 0x99 or C was originally 1) ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=The%20Game%20Boy%20STOP%20instruction,the%20second%20byte%20is%20ignored)). DAA operates as a single instruction (1 cycle). It does have *global state* dependency in that it uses the flags from the previous arithmetic operation. For example, after adding two BCD digits with a half-carry, DAA will see H=1 and add 0x06 to fix the low digit. **Exception:** DAA is only defined to produce correct results if A contained a proper BCD result beforehand; using DAA arbitrarily can yield unspecified results, but the flag logic is still applied as above. From an implementation view, DAA is one of the more *irregular* instructions since it branches logic based on prior flag state.

- **Complement (CPL):** A logical NOT on A (flip all bits of the accumulator). This is a simple bitwise operation: `A = ~A`. Flags: Z and C are unaffected, N and H are set to 1 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=CCF%3A%20Complement%20carry%20flag%20Flips,the%20N%20and%20H%20flags)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode)). (On Game Boy, executing CPL always sets the **N** and **H** flags to 1 – this mirrors Z80 behavior of marking that an adjust operation was done.) It’s implemented in one micro-op (bit invert) and has no timing complexity (1 cycle). No further state implications, aside from flags being updated in this fixed way.

- **Set Carry Flag (SCF) & Complement Carry (CCF):** These are flag-only operations. 
  - **SCF:** Sets the carry flag C to 1, and clears N and H flags (N=0, H=0) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=SCF%3A%20Set%20carry%20flag%20Sets,the%20N%20and%20H%20flags)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,C%20%3D%201)). Z is unaffected. Essentially a primitive that directly manipulates the F register bits. No actual arithmetic is done on A. It’s 1 cycle.
  - **CCF:** Flips the carry flag (C = ¬C), and also clears N and H (N=0, H=0) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=CCF%3A%20Complement%20carry%20flag%20Flips,the%20N%20and%20H%20flags)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,flags.C)). Z remains unchanged. This can be implemented by reading the C flag, toggling it, and writing it back. On real hardware, CCF uses the previous C in H on some Z80s, but **on SM83 it simply resets H** (the Game Boy does *not* set H to old C – it just clears it ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode))). Both SCF and CCF are single-cycle. They don’t use the ALU except to affect flag bits. No special timing issues.

**Timing/State:** All 8-bit arithmetic/logic ops (ADD, ADC, SUB, SBC, CP, AND, OR, XOR, CPL, SCF, CCF) are 1-cycle (plus any memory access). Inc/dec on memory are 2-cycle due to read-modify-write. 16-bit ALU ops typically take 2 cycles (or 3-4 if an immediate or SP offset is involved). The half-carry flag (H) is a byproduct of the nibble-based adder; an emulator must calculate it correctly but doesn’t need to simulate the two-step nibble addition explicitly unless doing cycle-level modeling. **Dual-cycle ALU** usage is only notable in that 16-bit adds and memory read-modify-writes internally do two operations, which is reflected in their machine cycle count ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200x09%3A,C)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=result%2C%20carry_per_bit%20%3D%20H%20%2B,PC%20%3D%20PC%20%2B%201)). For software modeling, it’s enough to compute final results and flags.

**Exceptions/Quirks:** The DAA instruction stands out as it depends on prior flags and involves multiple conditional adjustments – it doesn’t fit the pattern of “result = f(A,operand)” followed by straightforward flag setting. Emulators must carefully implement the official algorithm for DAA. Another quirk: the **AND instruction setting H=1** is an arbitrary design choice; similarly, CPL forcing N,H=1 and SCF/CCF’s specific flag rules must be memorized – they don’t fall out of a generic ALU operation. These are exceptions to general flag behavior. Lastly, note that the **Z flag** is not affected by 16-bit adds (so one must be careful not to erroneously clear it); and INC/DEC 16-bit affect no flags at all, unlike their 8-bit counterparts – these inconsistencies need to be hardcoded.

## Rotate and Bit-Manipulation Primitives

The SM83 includes a set of bit-level operations (some via the 0xCB prefix) for rotates, shifts, bit testing, etc. These can be implemented with simple bitwise and bit shift primitives. Many of them update flags in unique ways. We enumerate the needed primitives:

- **Rotate Left Circular (RLC) 8-bit:** Moves the MSB (bit7) of a byte into the LSB (bit0) and also into the Carry flag. For example, RLC A will put A←((A<<1) | (A>>7)), and C = old bit7. We implement this by extracting bit7, shifting the byte left, and setting bit0 to the extracted bit7. Flags: Z is set if result is 0 (for rotate instructions on registers via the CB prefix; however, the accumulator-specific `RLCA` sets Z=0 by definition) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00000111%2F0x07%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Length%201%20byte%3A%20opcode%20Flags,%EF%80%85%20Simple%20timing%20and%20pseudocode)). N=0, H=0 always, C = old bit7 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00000111%2F0x07%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)). So two variants exist:
  - **RLCA/RLCA (accumulator A only, opcodes 0x07/0x0F):** These are 1-byte instructions that do RLC/RRC on A *but* they do **not set Z** (Z flag is left as it was or always 0) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=RLCA%3A%20Rotate%20left%20circular%20,TODO)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00000111%2F0x07%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)). On Game Boy, after RLCA or RRCA, Z is documented as 0 (since A cannot be zero if you rotate its bits unless A was 0, but GB manual simply forces Z=0) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00000111%2F0x07%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)). Emulate by performing the rotate and then setting N=H=0, C accordingly, and **force Z=0**.
  - **RLC r / RLC (HL) (CB-prefix opcodes):** These rotate any register or the value at (HL). They *do* update Z if the result is zero, and set flags N=0,H=0,C=old bit7. The primitive operation is the same bit manipulation. We just must handle the flag difference.

- **Rotate Left through Carry (RL) 8-bit:** Similar to RLC but instead of cycling bit7 to bit0, it shifts left and brings in the **old Carry flag** into bit0. For example, RL E: new bit0 = previous C flag, C = old bit7. We implement by capturing bit7, shifting left, inserting old carry into bit0. Flags: Z set if result = 0 (except `RLA` where Z is not affected), N=0, H=0, C = old bit7 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=RLA%3A%20Rotate%20left%20)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00010111%2F0x17%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)). The distinction again is:
  - **RLA/RRA (accumulator opcodes 0x17/0x1F):** Do the through-carry rotate on A, but Z is not modified (Game Boy sets Z=0 for these) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=RLA%3A%20Rotate%20left%20)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00010111%2F0x17%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)). 
  - **RL r / RL (HL) (CB-prefixed):** Rotate through carry on any register/memory; set Z if result 0, N=0,H=0,C=old bit7.

- **Rotate Right Circular (RRC) 8-bit:** This is the mirror of RLC: LSB (bit0) moves to MSB and to Carry. Implementation: capture bit0, shift the byte right, put the captured bit0 into bit7, set C = old bit0. Flags: Z set if result 0 (except `RRCA` forces Z=0), N=0, H=0, C = old bit0 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=RRCA%3A%20Rotate%20right%20circular%20,TODO)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=TODO)).

- **Rotate Right through Carry (RR) 8-bit:** Similar to RRC but bit7 is filled with the old Carry flag, and C gets old bit0. We shift right, insert old C into bit7. Flags: Z set if result = 0 (except `RRA` where Z unaffected), N=0, H=0, C = old bit0 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=RRA%3A%20Rotate%20right%20)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00011111%2F0x1F%20Duration%201%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)).

The rotate primitives can be summarized as two operations (rotate left or right) with a mode (circular vs through-carry). In implementation, it’s convenient to have a function that takes a byte and the Carry flag and returns a rotated byte and a new Carry. All rotate instructions execute in 1 cycle for A (or 2 cycles for CB prefix targeting other registers or (HL)). 

**Micro-ops breakdown:** For example, `RL C` (CB 0x11) does: read C, compute new_val = (C<<1) | (carry_in) with carry_in from old C flag, determine new carry_out = old bit7 of C, write back C = new_val, then set flags Z (if new_val=0), N=0, H=0, C = carry_out. If broken into smaller steps: bit extract, bit merge, flags set – but it’s already minimal logic.

- **Arithmetic Shifts Right (SRA) 8-bit:** Shifts a byte right by 1, preserving the sign bit (bit7 remains the same after shift). Implementation: capture bit0 (for Carry), and bit7, then do `val >>= 1`, then set bit7 back to itself (so it stays the same). Flags: Z=1 if result 0, N=0, H=0, C = old bit0. For example, if A = 0x81 (1000_0001b), SRA yields 0xC0 (1100_0000b) and C=1. This is a single-bit shift primitive. Takes 2 cycles if via CB opcode. No special cases, except that the MSB doesn’t clear. (There is no accumulator-specific SRA; only via prefix.)

- **Logical Shift Right (SRL) 8-bit:** Shifts right and inserts 0 into bit7 (i.e. does not preserve sign). Implementation: capture bit0, shift right, set bit7 = 0. Flags: Z set if result 0, N=0, H=0, C = old bit0 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=SRL%20r%3A%20Shift%20right%20logical,TODO)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00111xxx%2Fvarious%20Duration%202%20machine,%EF%80%85%20Simple%20timing%20and%20pseudocode)). Essentially, this is like dividing by 2 for unsigned values. No special state issues. (CB opcode only.)

- **Shift Left (Arithmetic) (SLA) 8-bit:** Shifts a byte left by 1; bit0 gets 0. (On Game Boy, SLA is effectively the only left shift, identical to a logical left shift since sign bit handling isn’t distinct on left shifts.) Implementation: capture bit7 for C, do `val <<= 1`, set bit0 = 0 (though shifting left already put 0 in LSB). Flags: Z if result 0, N=0, H=0, C = old bit7. E.g. 0x80 (1000_0000b) SLA -> 0x00 with C=1 and Z=1. No special cases. 2 cycles via CB.

- **Swap Nibbles (SWAP) 8-bit:** Exchanges the high 4 bits and low 4 bits of a byte. For example, 0x3C (0011_1100) becomes 0xC3 (1100_0011). We implement this by `(val << 4) | (val >> 4)`. Flags: Z=1 if result is 0; N=0, H=0, C=0 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=SWAP%20r%3A%20Swap%20nibbles%20,TODO)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b00110xxx%2Fvarious%20Duration%202%20machine,0%20Simple%20timing%20and%20pseudocode)). It always clears C (in fact, after SWAP, C is 0 by definition). This is one 8-bit operation. It takes 2 cycles (for registers or (HL) via CB prefix). No further micro-ops needed beyond swapping bits. No special hardware implications.

- **Bit Test (BIT b, r):** Tests a specific bit in a register or memory (0-7). It does this by isolating that bit (e.g. by `value & (1<<b)`) and setting flags accordingly. The result of the bit test is not stored (the operand is unchanged), but Z flag is set if the tested bit was 0 (meaning the bit is clear) and reset if the bit was 1 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=BIT%20b%2C%20r%3A%20Test%20bit,TODO)). Flags: Z = !((val >> b) & 1) (i.e. Z=1 if bit is 0) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=BIT%20b%2C%20r%3A%20Test%20bit,TODO)); N=0; H=1; C is *not affected* (crucially, BIT does not change Carry) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=BIT%20b%2C%20r%3A%20Test%20bit,TODO)). This behavior is consistent with Z80: BIT is like an AND with a mask that doesn’t write back, but always sets H=1 and N=0, and preserves C. So the primitive needed is: “test bit b of value, update flags accordingly”. We can implement without actual ALU arithmetic – just a shift or mask. BIT instructions take 2 cycles (or 3 if (HL) is used due to an extra memory read). Micro-ops: read operand (does not modify it), set flags as above.

- **Bit Set/Reset (SET/RES b, r):** These instructions modify a single bit of a register or memory:
  - **SET b,r:** Sets bit b to 1. Primitive: `val |= (1<<b)`. 
  - **RES b,r:** Resets bit b to 0. Primitive: `val &= ~(1<<b)`. 
  After the operation, the value is written back to the register or memory. **Flags are not affected at all** (flags remain exactly as before) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b10xxxxxx%2Fvarious%20Duration%202%20machine,Simple%20timing%20and%20pseudocode)). In particular, these do *not* set Z even if the result happens to be 0 – they simply perform the bit edit. They break down to a read (if (HL)), a bitwise operation, and a write (if (HL)). They are 2 cycles for register targets, 4 cycles for (HL) (due to the read-modify-write sequence). No special timing beyond that. No global state issues; they’re purely combinatorial bit ops.

**Timing/State:** All these bit/rotate/shift ops are executed via the 0xCB prefix (except the four accumulator rotates). The prefix itself causes an extra opcode fetch cycle. In an emulator, this just means you’ll decode a second byte after seeing 0xCB. Each of these operations then may do a memory read or write if needed. Notably, **the accumulator rotates (RLCA/RLA/RRCA/RRA)** are single-byte opcodes that run in 1 cycle and do *not* update Z, whereas the prefixed versions set Z. The emulator must handle this difference in flag logic explicitly. None of these instructions depend on or modify any global CPU state beyond the flags (and the documented register results). 

**Exceptions/Quirks:** The flag behaviors are somewhat unique for certain bit ops: BIT setting H=1 regardless of the data is a bit unusual but must be honored ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=BIT%20b%2C%20r%3A%20Test%20bit,TODO)). The accumulator rotations forcing Z=0 is a special-case rule – one must not accidentally set Z if A becomes 0 (e.g. rotating 0x00 still leaves Z=0, which is an exception since normally result 0 sets Z). The implementation is otherwise straightforward. There are no known hardware bugs specific to these operations aside from obeying the general fetch/execute cycle (the 0xCB prefix effectively acts like a separate decode stage). Because these are mostly pure combinatorial bit logic, they map cleanly to software bit operations.

## Stack Manipulation Primitives (Push/Pop)

The Game Boy CPU uses a stack pointer (SP) and memory for stack operations. **Push** and **Pop** are implemented with a combination of 16-bit register access and memory writes/reads. The primitives needed are: adjusting SP and performing memory transfers. The stack grows downward (push decrements SP, pop increments SP) in Game Boy memory.

- **PUSH rr (Push 16-bit register pair):** Takes a 16-bit register (BC, DE, HL, or AF) and pushes its value onto the stack. In micro-operations, this is broken into two 8-bit writes:
  1. Decrement SP by 1, and write the **high-order byte** of rr to memory at the new SP address.
  2. Decrement SP by 1 again, and write the **low-order byte** of rr to memory at that address ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,1%20write_memory%28addr%3DSP%2C%20data%3Dlsb%28BC)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=SP%20%3D%20SP%20,1%20write_memory%28addr%3DSP%2C%20data%3Dlsb%28BC)).
  The result is that SP has been reduced by 2, and the 16-bit value is stored at memory[SP] (low byte) and memory[SP+1] (high byte). For example, `PUSH HL` with HL=0x1234 and SP starting at 0xD000 will write 0x12 to 0xCFFF and 0x34 to 0xCFFE, leaving SP=0xCFFE. No flags are affected by PUSH. Timing is 4 machine cycles ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b11xx0101%2Fvarious%20Duration%204%20machine,Simple%20timing%20and%20pseudocode)), corresponding to the two memory writes and overhead. On hardware, the push operation is atomic (an interrupt cannot occur in the middle of the two writes). In an emulator, one must be sure to decrement SP in the correct order and use the correct byte order (high byte first) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=SP%20%3D%20SP%20,1%20write_memory%28addr%3DSP%2C%20data%3Dlsb%28BC)).

- **POP rr (Pop 16-bit register pair):** Pops two bytes off the stack into a 16-bit register. Micro-ops:
  1. Read the low-order byte from memory at address SP, store it as the low 8 bits of rr, then increment SP by 1.
  2. Read the high-order byte from memory at the new SP, store as high 8 bits of rr, then increment SP by 1 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200xC1%3A,1%3B%20BC%20%3D%20WZ)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200xC1%3A,1%3B%20BC%20%3D%20WZ)).
  This effectively reverses the PUSH. For example, `POP BC` with SP=0xCFFE should read memory[0xCFFE] into C, and memory[0xCFFF] into B, then SP becomes 0xD000 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200xC1%3A,1%3B%20BC%20%3D%20WZ)). No flags are affected *except* in the case of popping into AF: the low byte is F (flags register), and the four lower bits of F are not real flags (they are always zero on hardware). When `POP AF` executes, the lower nibble of the value loaded into F should be masked out (in actual hardware, those bits are zeroed). Emulators often implement `POP AF` by masking `value & 0xF0` after the pop. Aside from that peculiarity, POP doesn’t set flags; it just restores them if AF is popped.
  Timing is 3 cycles for POP (two memory reads). The operation should be considered atomic as well. 

**Note on AF’s lower bits:** The Game Boy’s F register uses only bits 7-4 for Z,N,H,C flags. Pushing AF will store those bits (with lower 4 bits as 0) to memory, and popping AF should ensure those 4 bits are zero. It’s a minor nuance when emulating but important for accuracy.

**Stack Pointer (SP) use:** The SP itself can be read/written by other instructions (as seen with LD HL,SP+e or LD (nn),SP), but for push/pop it’s implicitly updated. These primitives require the ability to do 16-bit addition/subtraction on SP (which we have from earlier arithmetic primitives) and memory access. In hardware, the SP decrement/increment and memory access are tightly coupled in the machine cycles ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,1%20write_memory%28addr%3DSP%2C%20data%3Dlsb%28BC)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%20if%20IR%20%3D%3D%200xC1%3A,1%3B%20BC%20%3D%20WZ)).

**Exceptions:** Push/Pop are generally straightforward. One tricky behavior: If an **interrupt occurs** right after a PUSH or POP has partially executed (midway), hardware would complete the instruction first – emulation doesn’t usually need to worry about this since we execute instructions atomically. There is no condition code involvement. However, misuse of `POP AF` with an invalid value could set undefined flag bits (emulators should mask them out). Also, if the stack pointer is misaligned (odd address) and you do a 16-bit push/pop, it will still work – there’s no alignment requirement, although typically code keeps SP word-aligned.

## Program Control Flow Primitives

Control flow instructions change the PC (program counter) and/or utilize the stack for subroutine calls. The minimal primitives here include: updating PC (for jumps/calls), performing relative offset addition, doing stack push/pop of PC for calls and returns, and evaluating condition flags. The SM83 supports conditional jumps/calls/returns, which require a primitive to check flag conditions and possibly skip the action. Timing can vary depending on whether the branch is taken or not, which we will note.

- **Unconditional Jump (JP nn):** Loads a new 16-bit address into PC, causing execution to continue from that address. Implementation: fetch the low-byte and high-byte of the target address from the instruction stream, then set `PC = nn`. This uses a 16-bit immediate operand and a direct assignment to PC. It’s a single micro-op to assign PC (after the bytes are read). Flags are not affected. Timing is 3 cycles (for reading 2 bytes and writing PC). In an emulator, after setting PC, the next fetched opcode will be from the new location (make sure to handle that jump in the flow).

- **Jump Relative (JR e):** Adds a signed 8-bit offset to the current PC to jump a short distance. Implementation: fetch the offset byte (interpreted as two’s complement), then do `PC = PC + offset`. In practice, PC is incremented past the offset byte, then offset is added. We can use an 8-bit signed addition primitive here. E.g. if PC after fetching offset = 0x0100 and offset = 0xF6 (-10 decimal), the new PC becomes 0x0100 + (-10) = 0x00F6. No flags are changed by JR. It takes 2 cycles (one for opcode+offset fetch, one for the actual jump calculation). The **primitive** is essentially a 16-bit add: (PC ← PC + immediate_signed). Since it’s only one byte, it only affects PC’s lower 8 bits potentially carrying into the high. No special hardware issues – it’s simpler than JP in that it’s relative.

- **Conditional Jumps (JP cc, nn and JR cc, e):** These instructions check a condition (cc) based on flag status and either perform the jump or continue sequentially. The condition primitives are:
  - **Flag check:** The conditions are Z (zero), NZ (non-zero), C (carry), NC (non-carry). Implement as a boolean evaluation of the F register. For example, NZ is true if Z flag is 0. 
  - If the condition is true, the jump is performed (using the same primitive as JP or JR above). If false, the jump is skipped and execution just falls through. In an emulator, you would still have consumed the operand bytes (for JP, both address bytes are usually fetched regardless; for JR, the offset is fetched regardless) but simply not modify PC if the condition is false. On the real hardware, the timing differs: a taken branch costs more cycles than not taken. For instance, `JR cc` is 3 cycles if taken, 2 if not taken. `JP cc` is 4 cycles if taken (because it does the jump) or 3 if not (still fetched the address) – the Game Boy’s documented timing reflects that the PC assignment takes an extra cycle.
  - In terms of micro-ops: The CPU will fetch the operands in any case. Then it checks the flag. If the condition is false, no change to PC (other than having read past the operands). If true, assign to PC (for JP) or add offset (for JR). Emulation must ensure PC is correct in both cases (for not-taken JP, PC will already have advanced past the 2-byte address, so effectively it just continues; for not-taken JR, PC is past the offset, effectively skipping it).
  - **No flags are modified** by the jump instructions themselves. The condition evaluation reads global state (ZF or CF). 
  - Special case: Jump conditions have no exceptions except that the conditional logic must use the flags as set by the previous instruction. If an interrupt were to occur in between (it can’t, since jump is one instruction), there’s no oddity.

- **Calls (CALL nn):** Calls are like jumps but first push the current PC (address of the next instruction) onto the stack for later return. Implementation uses a combination of the push and jump primitives:
  1. Fetch 16-bit target address nn.
  2. Compute the return address (the address of the instruction after the call). In an emulator, this is basically the current PC value after reading nn (pointing to the next instruction).
  3. Push the 16-bit return address onto the stack (high byte, then low byte) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20R%3A%20lsb,PC%E2%82%80%2B3)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=write_memory,PC%29%29%20PC%20%3D%20nn)).
  4. Set PC = nn to jump to subroutine ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,PC%29%29%20PC%20%3D%20nn)).
  This uses the push primitive (with PC as the value to push) and the jump primitive. In hardware, CALL is 6 cycles ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=Opcode%200b11001101%2F0xCD%20Duration%206%20machine,Simple%20timing%20and%20pseudocode)). In software, just ensure to push PC correctly *before* altering PC to the target. No flags are affected by CALL itself. 
  - **Conditional CALL (CALL cc, nn):** Similar to CALL but only executes the push and PC change if the flag condition is true. If condition is false, the instruction does nothing besides increment PC past the 2-byte address. Timing if not taken is 3 cycles (just like a JP not taken, because it still had to read the address), if taken it’s 6 cycles (like an unconditional call). Emulate by: check flag, if false skip push/jump; if true, do the steps above. 
  - *Global state:* The act of pushing PC uses SP and memory, but nothing special beyond that. Do note that if an interrupt fires immediately after the CALL, it will occur after the call has fully completed (the entire push and PC set). 

- **Return (RET):** Returns from a prior CALL. This pops the 16-bit address from the stack into PC. Implementation: perform a 16-bit pop into PC (pop two bytes into PC low and high) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=lsb%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)). After this, execution continues from that PC. No flags are modified by RET itself. Timing is 4 cycles. Essentially it’s the inverse of CALL: uses the POP primitive on PC. In micro-ops: increment SP, get low, increment SP, get high, combine into PC ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)). 
  - **Conditional RET (RET cc):** Checks a flag and returns only if condition true. If false, it just consumes 1 cycle (RET cc not taken is faster – 2 cycles – since it doesn’t pop) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj)). If true, it does the pop (5 cycles total on hardware). Emulate by flag check, if true do pop into PC, if not, do nothing to PC. (On hardware, a not-taken RET cc actually takes 2 cycles, presumably just fetching and doing nothing else.)

- **RETI (Return from Interrupt):** This is a return that also re-enables interrupts. Operationally, it performs a normal 16-bit pop into PC (just like RET) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=lsb%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)), then sets the global IME (Interrupt Master Enable) flag to 1 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=PC%20%3D%20unsigned_16,1)). In microcode: pop PC, then IME←1. Timing is 4 cycles (same as RET). The IME setting means that after RETI, interrupts are back on (this is used at the end of an interrupt service routine). Emulators implement RETI by calling the same routine as RET, then setting IME=1. Important: On real hardware, RETI *unmasks* interrupts immediately – any pending interrupt will not be serviced until the next instruction starts (the RETI itself is just finishing), so effectively immediately after RETI, interrupts can trigger. There’s usually no special hazard except to ensure IME is enabled at the end. (In contrast, the normal `EI` instruction doesn’t enable IME until after the *next* instruction – RETI is an exception that enables it right away ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=RETI%3A%20Return%20from%20interrupt%20handler,enables%20interrupts%20by%20setting%20IME%3D1)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)).)

- **RST (n):** Restart is a one-byte call to a fixed address. It pushes the current PC on stack and jumps to address n (00h,08h,10h,...38h). It can be seen as a shorthand for `CALL n` with only one byte. Implementation: Take the current PC (after the RST opcode, which is the next instruction address) and push it, then set PC = n ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20W%3A%20msb%20PC%20W%3A,lsb%20PC)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=n%20%3D%200x18%20SP%20%3D,lsb%3Dn%2C%20msb%3D0x00)). The push and PC set are identical to CALL’s behavior, just that the target address is hardcoded by the opcode (the three least significant bits of the opcode times 8). For example, opcode 0xDF is RST 18h – it will push PC and set PC=0x0018 ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20W%3A%20msb%20PC%20W%3A,lsb%20PC)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=n%20%3D%200x18%20SP%20%3D,lsb%3Dn%2C%20msb%3D0x00)). Timing is 4 cycles (faster than a full CALL since no operand fetch needed). No flags are affected. RST is typically used for interrupt vectors and common subroutines.

**Fetch-Execute Overlap:** On the Game Boy CPU, the instruction fetch for the next instruction is often overlapped with the last cycle of the current instruction. For jumps and calls, this is mostly invisible to software, but one edge case involves **DI/EI and interrupts** (discussed below). The pseudocode in the technical reference shows that after a jump or branch decision, a `fetch_cycle` may be invoked ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%2FM1%20if%20IR%20%3D%3D%200xF3%3A,1%3B%20IME%20%3D%200)). For emulation, it suffices to update PC appropriately; the next loop iteration will naturally fetch from the new PC.

**Variable Timing:** As noted, conditional instructions have different timings when taken vs not taken. An emulator not concerned with cycle accuracy can ignore this, but for cycle-accurate emulation, one must add cycles for the taken-branch case. For example, if implementing a step-by-step emulator, after a JR cc, add 1 extra cycle if the jump was taken. This reflects the extra internal operation of updating PC.

**Exceptions:** Generally, flow control is straightforward. One important quirk on real hardware is the **HALT bug** interaction with interrupts and PC, which is covered under the HALT instruction below. Also, after a `JP (HL)` (jump indirect via HL) or after any jump, there’s no special pipeline refill delay beyond what’s already accounted for in cycle counts. The **IME (interrupt enable)** behavior after `EI` or `RETI` must be handled (see next section). Finally, note that performing a `CALL` or `RST` when the stack is near the end of RAM could overflow it – but that’s a program error, not CPU’s logic problem (the SM83 doesn’t prevent stack over/underflow).

## Interrupt and System Primitives

This category includes instructions that control CPU state: enabling/disabling interrupts, low-power halt/stop modes, and a no-operation. They don’t fit into ALU or flow control, but they have global effects.

- **DI (Disable Interrupts):** This instruction clears the Interrupt Master Enable flag (IME=0), which globally disables maskable interrupts ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=DI%3A%20Disable%20interrupts%20Disables%20interrupt,the%20EI%20instruction%20if%20any)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,0xF3%3A%20IME%20%3D%200)). In an emulator, this is a single step: IME←0. On hardware, DI also *cancels any pending EI enable* – i.e., if an `EI` was executed just before, scheduled to set IME after the next instruction, the DI will prevent that (the reference notes it “cancels any scheduled effects of EI” ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=DI%3A%20Disable%20interrupts%20Disables%20interrupt,the%20EI%20instruction%20if%20any))). This is a subtle point: `EI` doesn’t take effect until after one instruction, so if DI occurs in that interval, the interrupt enabling never happens. Timing: DI is 1 machine cycle. It doesn’t affect any flags (Flags “–”). It can’t be broken down further; it’s just a flip of a global bit. One nuance in hardware: immediately after DI, the interrupt check that normally happens at instruction boundaries is suppressed ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=M2%2FM1%20if%20IR%20%3D%3D%200xF3%3A,1%3B%20IME%20%3D%200)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20IR%20%3D%3D%200xF3%3A%20,1%3B%20IME%20%3D%200)), meaning an interrupt that was requested at the same moment will not be serviced. In an emulator, usually you set IME=0 and ensure no interrupt fires in between instructions (which is naturally handled by instruction-step loop).

- **EI (Enable Interrupts):** EI sets the IME flag to 1 **after the next instruction executes**. In other words, EI schedules IME=1 but does not immediately allow an interrupt in the very next instruction. This can be implemented by having a deferred flag (IME_next = 1). After executing one more opcode, the emulator should set IME to 1. In practice, many emulators handle this by flipping IME at the end of the EI instruction but then ignoring any interrupt for one cycle – or by explicitly tracking a “just enabled” state. The provided pseudocode shows `IME_next = 1` on EI, and then the next instruction’s fetch cycle sets IME=1. Timing: EI is 1 cycle, no flags changed. If an interrupt becomes pending right after EI, it will only be serviced after the subsequent instruction. (This delay prevents an interrupt routine from immediately interrupting the code right after EI.) If an EI is immediately followed by a DI in code, the DI will cancel the scheduled enable as mentioned. In summary, the primitive here is: set a internal boolean to enable IME on the next cycle boundary.

- **HALT:** Puts the CPU into a low-power standby mode where the CPU clock is halted until an interrupt occurs. In an emulator, HALT can be modeled by a state where you stop executing new instructions and wait for an interrupt request (IF flag) that is enabled (IE and IME allowing it). When such an interrupt occurs, the CPU exits the halt and will service the interrupt (or resume execution if interrupts were disabled). HALT is tricky because of a known **halt bug**: if IME=0 (interrupts disabled) at the time of HALT, and no interrupt is pending, the CPU doesn’t truly halt – it **continues execution with a glitch**. Specifically, on classic Game Boy models, the next instruction is fetched twice, causing an effective duplicate of the next opcode byte ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=The%20,For%20example)). For example, if a HALT is followed by an `INC B` and interrupts are off, the CPU will execute INC B *two times* ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=The%20,For%20example)). This is an observable hardware quirk that emulators often must replicate for certain test ROMs. So:
  - **Normal behavior (IME=1 or an interrupt is pending):** CPU stops at HALT and does not increment PC to the next instruction. It will remain in place until an interrupt fires. When an interrupt occurs, if IME was 1, the CPU will wake and service it (the PC at wake is still at HALT’s next instruction). If IME was 0 but an interrupt became pending during halt, the CPU will wake without servicing (since IME=0) and simply resume with the next instruction – this scenario triggers the bug effect.
  - **Bug behavior (IME=0 with no pending interrupt):** The CPU erroneously doesn’t halt. Instead, it proceeds as if to execute the next instruction *but PC doesn’t advance properly*. The next opcode is read twice ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=The%20,For%20example)). In effect, PC remains the same, so the next instruction is executed, then on “return” from the phantom halt, it executes that same instruction again. This is a very special-case event. (The recommended workaround is to put a NOP after HALT when interrupts are off ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=halt%20inc%20b%20%3B%20B,is%20a%201%20byte%20instruction)).)
  - In software terms, to emulate HALT: one can set a `halted = true` state and stop the CPU loop until an interrupt condition. If IME=0 and IF (interrupt flags) is 0 at the moment of HALT, you may implement the halt bug by immediately incrementing PC by 1 (skipping the next byte) or executing the next instruction twice. The Wikiversity description says “the instruction counter will duplicate the next byte, and read it twice” ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=The%20,For%20example)) – meaning PC doesn’t advance, effectively re-reading the opcode. This is complex but known.
  - HALT itself doesn’t change any flags or registers (aside from the PC quirk). It’s not an arithmetic or control instruction in the normal sense – it’s an operation mode.
  - From a primitive perspective, we need: the ability to pause execution until a condition (interrupt) occurs, and the ability to handle the halt bug scenario. No smaller micro-ops within HALT except checking IME/interrupt status.
  - Timing: HALT formally takes 1 cycle to execute the opcode, then the CPU enters a halted state consuming no further cycles until an interrupt (the system clock is stopped). The resumption is effectively immediate when an interrupt happens (the interrupt servicing then takes its normal cycles).

- **STOP:** This instruction is intended to stop *both* the CPU and the main oscillator. On the DMG (original Game Boy), STOP will halt the system (screen off, CPU off) until a button is pressed. On the CGB (Game Boy Color), STOP is repurposed to toggle the double-speed mode if the appropriate register (KEY1) is set, otherwise it behaves similarly to DMG. Implementation:
  - In an emulator, STOP can set a state `stopped = true` where the CPU ceases execution until an external event (like a joypad press or in CGB, a speed switch) occurs. Typically, you also set PC = PC+1 because STOP is documented as a 2-byte instruction: the next byte (often `00`) is a placeholder. The second byte is officially “ignored” ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=The%20Game%20Boy%20STOP%20instruction,the%20second%20byte%20is%20ignored)), but due to quirks, if it’s not 00 the behavior can glitch.
  - If the emulator is for CGB, you check the key1 register: if a speed switch is pending (key1’s bit0 = 1), executing STOP will toggle the speed mode (and clear the bit) ([Reducing Power Consumption - Pan Docs - gbdev.io](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=Reducing%20Power%20Consumption%20,normally%20causes%20a%20speed%20switch)) ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=The%20Game%20Boy%20STOP%20instruction,the%20second%20byte%20is%20ignored)). In this case, the CPU doesn’t remain stopped; it resumes immediately at double or normal speed (with PC advanced past the STOP). If no speed switch is pending, or on DMG, STOP will freeze until a button press (which on real hardware triggers an interrupt-like wakeup).
  - STOP does not affect flags or registers. It just halts the system. On hardware, one must ensure LCD is off or it can cause a line on screen or hang (there are various hardware caveats ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=No%20licensed%20rom%20makes%20use,use%20of%20the%20STOP%20instruction)) ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=The%20Game%20Boy%20STOP%20instruction,the%20second%20byte%20is%20ignored)), but for emulation, mainly handle the speed switch and pause).
  - The instruction is 1 byte followed by a 1-byte padding (usually 0x00). The padding byte is consumed but not used. A known quirk: if the padding is not 00h, some older models may misinterpret STOP as a different instruction or behave oddly ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=2,byte%20is%20ignored)). Emulators typically just increment PC by 1 extra and ignore the value.
  - In summary, implement STOP by checking CGB mode for speed switch (if yes, toggle speed and continue), else pause until joypad input (one could emulate this by waiting for an interrupt or a specific input event).
  - From a primitive viewpoint, STOP is like a “global system state change” primitive (enter stop mode). 

- **NOP:** No Operation. This does nothing except advance PC by 1. It can be seen as a filler instruction with no side effects. Primitive: none (just a placeholder). Flags not touched. Timing: 1 cycle. NOP is useful for padding and delay, but it doesn’t require any special handling in emulator beyond simply doing nothing.

- **Prefix CB:** Although not an “instruction” by itself to the programmer, 0xCB is an opcode that signals an extended instruction set (the bit/rotate operations discussed). In a decoder, one must handle this by reading the next byte and decoding it as a separate instruction. In a sense, the primitive here is the **instruction decode unit logic** that allows a two-byte opcode. The fetch of 0xCB can be considered a micro-op that changes the opcode map for the next byte. Timing-wise, the prefix consumes 1 cycle by itself and then the next byte’s instruction takes its cycles. In emulation, you’ll typically handle this in the instruction switch-case: if opcode == 0xCB, fetch next opcode and dispatch to the bit/rotate handler. It doesn’t affect flags or registers by itself.

**Global State & Interrupts:** The IME flag controls whether the CPU will accept maskable interrupts. When IME=1 and an interrupt is requested (and enabled in the IE register), the CPU will execute an interrupt vector (which is essentially a RST call) at the next appropriate moment (after the current instruction or after HALT wakes). Emulating this requires checking interrupt flags each instruction or each cycle. Notably:
- After an `EI`, we must delay setting IME=1. An interrupt that becomes pending right after EI will only fire after one more instruction has executed.
- After a `DI`, interrupts will be ignored until a later EI.
- The **RETI** instruction sets IME=1 immediately upon return ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)) ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=lsb%20%3D%20read_memory,lsb%3Dlsb%2C%20msb%3Dmsb%29%20IME%20%3D%201)), so an interrupt that occurs just as RETI finishes could in theory be serviced immediately (some testing indicates the next instruction can be interrupted).
- If the CPU is in **HALT** with IME=0, an interrupt becoming pending will cause HALT to exit (because an interrupt request *wakes* the CPU even if it can’t execute it). This results in the halt bug behavior: PC doesn’t advance but execution resumes. Emulators typically implement this by: if HALT and IME=0 and IF&IE=0 (no interrupt pending), trigger the halt bug (PC←PC, effectively execute next twice). If HALT and any interrupt is pending (IF&IE != 0) but IME=0, then exit halt mode and continue (skip next instruction? Actually on real hardware, it does **not** skip – it resumes normally but without servicing the interrupt; the act of request woke it).
- When an interrupt is serviced (which isn’t a direct “instruction” but an event), the CPU performs a push of PC and jump to vector similar to RST. This is outside normal program flow. But since the question is about the instruction set’s primitives, we note that the **interrupt handling sequence** uses the same primitives: it internally does `PUSH PC` and `PC = vector` (and clears IME). Emulators often implement this in the main loop when an interrupt is detected with IME=1.

**Exceptions/Quirks:** We’ve covered the major tricky behaviors: the HALT bug ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=The%20,For%20example)), the STOP mode variations ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=The%20Game%20Boy%20STOP%20instruction,the%20second%20byte%20is%20ignored)), and the EI delay. Another edge case: double STOP or HALT instructions back to back. Two HALTs in a row with interrupts disabled will lock the CPU (second HALT never exits because the first one didn’t properly halt – a pathological scenario) ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=Odd%20behavior%20will%20occur%20if,the%20user%20to%20reset%20it)). Also, if using STOP on DMG without proper conditions, it might not actually stop the screen (as Pan Docs warns) ([Reducing Power Consumption - Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#:~:text=No%20licensed%20rom%20makes%20use,use%20of%20the%20STOP%20instruction)). These are hardware oddities not usually needed for functional emulation, except the HALT bug which some software exploited. 

Finally, none of these system instructions affect the arithmetic flags, except as noted for CPL/CCF/SCF in the logic section. And none of them besides RETI and EI modify IME (DI clears it, EI schedules it, RETI sets it). NOP truly does nothing. 

---

**In summary**, implementing the Game Boy’s SM83 instruction set in software requires the following core primitives:
- *Memory access:* read and write bytes, with variants for immediate operands and indirect addressing modes.
- *Register transfer:* moving data between CPU registers and between registers and memory.
- *8-bit ALU operations:* add, adc, sub, sbc, and, or, xor, cp, complemented by flag calculations (zero, carry, half-carry, subtract).
- *16-bit arithmetic:* primarily addition (with proper half-carry and carry flag handling) and simple increment/decrement without flags.
- *Bit ops:* bit rotates (through carry or circular), shifts, bit test, set, reset, and nibble swap.
- *Stack ops:* push and pop using memory writes/reads and SP update.
- *Control flow:* updating PC for jumps/calls (with relative address addition for JR), pushing/ popping PC for calls/returns, and evaluating flag conditions.
- *System state:* manipulating the IME (global interrupt enable) and halting or stopping the clock, including correctly emulating the timing quirks of EI (delayed enable), HALT (interrupt behavior and bug), and STOP (CGB speed switch and wake-up).

Each Game Boy instruction can be composed from these primitives. By accurately modeling flag updates (especially half-carry and carry from the proper bit positions ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=if%20opcode%20%3D%3D%200x90%3A%20,7%5D%20else%200))) and global states (IME, halt state), one can ensure the emulator behaves like real hardware. The major exceptions – such as the HALT bug and the interaction of STOP with hardware state – have been noted and should be handled explicitly as they don’t generalize from normal instruction behavior. With this comprehensive set of primitives and careful attention to the noted special cases, the entire Sharp SM83 instruction set can be implemented to match cycle-accurate hardware effects ([gbctr.pdf](file://file-9opA2Y7yehkkafDj4YLYjj#:~:text=opcode%20%3D%20read_memory,7%5D%20else%200)) ([Programming for the Gameboy/Hardware errata and bugs - Wikiversity](https://en.wikiversity.org/wiki/Programming_for_the_Gameboy/Hardware_errata_and_bugs#:~:text=The%20,For%20example)).
